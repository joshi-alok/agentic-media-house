# Agentic Media House

Agentic Media House is a publication about AI agents in crypto, and the Desk is the pipeline that will write it. A piece will publish without a human only when a code-based gate finds no blocker (every number, date and quotation of a factual sentence traces to a quoted span of a source, and every factual sentence cites a claim) and an independent model check agrees that each factual sentence says what its sources say. Rules about length, shape, capitalised names and filler are notes: they are recorded on the receipts page of the piece and do not stop it. Anything the gate or the model check cannot clear will be held for the owner. This repository holds the gate, the ledger format, the renderer, the site and the Desk itself. The Desk is built and tested offline, with scripted models; it has not yet run against live sources or a live model, and nothing it writes has been published (see Which parts are live and The desk workspace).

The full design is in [`docs/superpowers/specs/2026-10-04-the-desk-design.md`](docs/superpowers/specs/2026-10-04-the-desk-design.md).

## Repository layout

| Path | What it is |
|---|---|
| `gate/` | `@robywire/gate`: pure functions implementing gate checks G1 to G9, and the renderer that turns a checked draft into a page. No network, no models. |
| `evals/` | `@robywire/evals`: the seeded-defect harness that proves the gate catches what it should. |
| `desk/` | `@robywire/desk`: the Desk pipeline, built and tested offline: the model layer, the seven stages, the orchestrator, replay, the command line and the verifier evals. |
| `site/` | `@robywire/site`: the Astro static site, and the scripts that audit it (`site/scripts/`). |
| `sources.yml` | The tiered source registry: where the Desk writes from and where it discovers stories. |
| `docs/` | Specs and plans, and the runbook (`docs/runbook.md`): the operations that put the publication on the air, each with its commands and what to expect. |

The workspace packages export their TypeScript source directly, so there is no build step for them.

## Source registry

`sources.yml` is the tiered registry of where stories come from.

- Tier 1 (primary) sources are what the Desk writes from: a project's, a company's or a researcher's own post, announcement or documentation, a paper, a filing, a standard or a proposal.
- Tier 2 (secondary) sources are what the Desk discovers from: other outlets' feeds that say something happened. The Desk never states a fact on their authority: a claim that only a tier 2 source gives may appear only as an attribution that names the outlet, and the article labels it Unconfirmed in its body. A headline or a description built on such a claim names the outlet and carries no label, and a piece may rest entirely on another outlet's reporting and be published without a human when the gate and the model check clear it.

If a story has no reachable tier-1 source, that fact goes in the piece. It is never quietly laundered through a competitor's reporting.

Every `status` starts as `unverified`, except the entries that the checks of 2026-10-20 found closed to the Desk, which are `blocked` with a note that says why, and `n/a` for the funding announcement, which has no fixed address. `desk sources-check` fetches every entry the way the Desk fetches and says which can be read; the statuses of the entries it could read are then `verified`. `gate/src/sources.ts` validates the file (`loadSources`) and `gate/test/sources.test.ts` checks it on every test run.

## Which parts are live

`site/src/lib/live.ts` is the switchboard for the parts of the Desk that do not yet run for real: the private evidence store (the Desk keeps its evidence in a folder on disk unless a file of settings asks for the bucket, which is built and tested against a stand-in that checks every signature, and has never been used against Cloudflare), the independent model check (built and tested with scripted models, and measured on no real model), the daily schedule (written as the workflow `.github/workflows/desk.yml`, which tests read and which has never run on GitHub) and the pipeline that writes and publishes (built and tested offline, and it has never published a real piece). Its four flags are all `false`. Every sentence of the site whose tense depends on one of them (the footer, the receipts intro, the home and feed descriptions, and most of the method page) is written by a function in `site/src/lib/copy.ts` that takes the switchboard, and `site/test/copy.test.ts` says what each function writes for all sixteen settings of the flags. It also fails if a page or another file writes such a sentence itself. When a part really runs, turn its flag on and let the tests name the sentences that change.

## The desk workspace

`desk/` (`@robywire/desk`) is the pipeline that will write the site. It is built and tested with no network and no API key: every test runs on made-up pages and a scripted model. `desk/test/setup/no-network.ts` runs before every test file and makes `fetch`, `net.connect`, `http.request` and `https.request` (and the lookup of a name) throw "network is not available in tests", so that a test that forgets to give the code a stand-in for the web fails at once and says what it tried to do. The guard is a safety net and not a proof: a test that started a child process that connects, or loaded a native module, could get through it. What keeps the tests offline is that each one gives the code its own stand-in.

- **Settings.** `desk/src/config.ts` has every setting of a run: how recent a story must be, how many candidates reach the selecting model, the fewest claims a piece needs, the rounds of revision and the one more round for a draft that only the model check rejects, the politeness of the fetcher, the budget of a run, the model for each role, the folders `runs/` and `evidence/`, and which evidence store a run keeps its snapshots in (`evidence.kind`: a folder or a bucket). `loadConfig` refuses a setting it does not know or a value that is not allowed.
- **Models.** One interface, `ModelClient`, that cannot express a tool, so no stage can offer a model one. A client that answers from a script (`FakeClient`), one that replays recorded replies (`RecordedClient`), one for the Anthropic API (`AnthropicClient`, tested only against a stand-in for the network), and wrappers for a budget and for retries. Text from the web reaches a model only inside delimited blocks, under a system prompt that says it is data.
- **Stages.** Discover, Select, Fetch, Extract, Compose, Verify, then Publish or Hold. Models propose and code disposes: code finds every quotation in the page and every claim's figures and names in its quotation, and holds every value's normalised form and unit to its raw text, the gate (`gate/`) checks every sentence, an independent model check judges meaning, and only what fails goes back to the composer, at most `maxRevisionRounds` times (twice by default) and `modelCheckRevisions` more times (once by default) for a draft that only the model check rejects; a gate blocker never gets the extra rounds. A claim from another outlet may appear only as an attribution that names the outlet, and the article labels it Unconfirmed in its body. Any error ends the run as `failed`, with nothing published.
- **A run.** Each stage writes its artifact into `runs/<date>/`, checked against a schema: `01-discover.json` to `06-verify.json`, a held draft in `held/`, the record `run.json` (which says how the run was made: which client answered the model, where the stories came from, and which try of its day it was), and the recorded model replies in `cassettes/`. The pages it read are kept by their hash in the evidence store (see The evidence store): the folder `evidence/`, unless the settings say a bucket. A run takes a lock. A day that published, was held or found no story is not run again unless `--force-new` says so; a day whose run failed is run again with no flag, up to `maxAttemptsPerDay` runs a day (3 unless the settings say otherwise, and the run after the last is refused); and the folder of an earlier run is kept beside the new one, as `runs/<date>.failed-<n>/` or `runs/<date>.replaced-<n>/`, never removed. Every run that is not dry makes exactly one commit on `main`: the piece, its ledger and the desk state for a piece that is published, and the desk state alone for a hold, a day with no story or a failure. A held piece that is sent to the owner also has one commit, of its two files, on a branch of its own (see Holds and corrections). Git ignores `runs/` and `evidence/`.
- **Replay.** `desk replay` runs Extract, Compose and Verify again from the pages in the evidence store and the recorded replies, and says whether each artifact is the one the run stored.

Not built, and left for the next plan: a command that keeps the snapshots of a piece that the owner released by merging a pull request, turning on the flags of `site/src/lib/live.ts` (and rewriting the copy that goes with them), tuning the prompts against a real model (the prompts are written, and `desk tune`, the command that measures them, is built and tested with scripted models and has never been run against a real one), measuring the verifier on a real model, and a client that uses a Claude subscription instead of an API key.

## The desk command

`npm run desk -- <command>` is the command line of the Desk (`tsx desk/src/bin.ts`). Run it from the root of the repository; everything after `--` goes to the Desk.

- `npm run desk -- run [--date YYYY-MM-DD] [--dry] [--client fake|recorded|api] [--sources fixtures|live] [--force-new] [--skip-if-done] [--cassettes <folder>] [--config <path>]` runs the pipeline once. A run that is not dry makes one commit; `--dry` writes the artifacts of the run and never touches `site/` or git. `--client api` (the default) needs `ANTHROPIC_API_KEY` in the environment; `--client recorded` replays the replies in `--cassettes`; `--client fake` is a scripted story. `--sources live` (the default) reads `sources.yml`; `--sources fixtures` is a made-up world with no network. The scripted client and the made-up world are only for dry runs, because nothing in them may be published. `--client api` with `--sources fixtures` is refused with exit code 2, dry or not: it would spend money on the answers of a model about pages that are made up, which are worth nothing (use `--client fake` for the scripted story, or `--sources live`). A day that published, was held or found no story is refused unless `--force-new` is given; a day whose run failed is run again with the same command, and the run after the `maxAttemptsPerDay`th of a day is refused (exit code 1, nothing run). `--skip-if-done` is for a schedule that starts the command more than once a day (see The daily workflow): a day that is done is then not an error but a day to leave alone. The command prints `outcome: refused-already-done` and exits 0, and runs nothing (asks no model, fetches nothing, writes nothing, and needs no key and no bucket), when the desk state says that the last run was of this day and did not fail, or when `runs/<date>/run.json` is there and says the same. The desk state is the record that a scheduled job has, because it starts from a fresh checkout and has no folder of runs. Every other refusal is still exit code 1, and `--skip-if-done` cannot be given with `--force-new`.
- `npm run desk -- replay <folder of a run> [--sources fixtures|live] [--client fake|recorded|api] [--cassettes <folder>] [--config <path>]` runs Extract, Compose and Verify again from what the run kept, with no network, and says whether the artifacts are the same. The record of the run says which client and which sources it used, so a replay needs no flag for them; `--sources` and `--client` are only checks, and one that contradicts the record is refused with exit code 2 (a replay with another registry would differ for that reason alone). A run made with `--client recorded` has no replies in its own folder, so replay it with `--cassettes`. A record from before records said how a run was made has no such information and needs `--sources`.
- `npm run desk -- status [--config <path>]` prints the last run (its outcome, its day and which try of the day it was), the number of holds, and the number of corrections and of retractions in the desk state. The try is read from the record of the run (`runs/<date>/run.json`), which only the machine that made the run has: when the record is not there, or is of another run, status says that the try is not known and why.
- `npm run desk -- sources-check [--items] [--config <path>]` fetches every entry of `sources.yml` as the Desk fetches (`robots.txt` honoured, at the pace of the settings, with the user agent of the settings) and says which can be read: one line for each entry with its result (`ok`, `robots`, `error`, `not-a-feed`, `empty` or `skipped`, the last for an entry whose status is `blocked`), the kind the registry gives it and what was found, then `N of M entries can be read; K were not tried`. `--items` lists under each feed its newest stories: for a primary feed, those that hold a keyword and link to a primary page (the pages to choose from); for an outlet, those that hold a keyword. An entry with no keywords has no filter, and its line says `no keyword filter` where the others count the items that hold a keyword. It writes nothing and needs no key, but it needs `--config` for the real user agent, as a live run does. Exit code 0 when every entry that was tried could be read, 1 when one could not, 2 for a mistake in the arguments or a user agent that links to an `.example` address.

- `npm run desk -- retract <slug> --reason <text> [--kind correction|retraction] [--dry]` records a correction (the default) or a retraction of a piece that is on the site, and commits it (see Holds and corrections).
- `npm run desk -- tune --urls <file> [--trials N] [--max-calls M] [--client api|fake] [--config <path>]` is the harness for the first trials with a real model, and for tuning what the model is told. It publishes and commits nothing (see The tuning harness).
- `npm run desk -- pack-artifact <folder of a run> <folder for the pack>` makes the small files that are uploaded as the artifact of a run in place of its folder (see The daily workflow). A folder of a run that is not there is no error.
- `npm run desk -- push [--branch-only] [--run-id <id>] [--output <file>] [--audit-log <file>]` pushes what the checkout has and `origin/main` has not, which is what a run committed, and is the step of the daily workflow that does it (see The daily workflow). Nothing to push is exit code 0; a push that went to the rescue branch, and every error, are exit code 1. `--run-id` names the rescue branch, `--output` is the file to which the line `pushed=true` is added when the commits were pushed. `--branch-only` is for commits that must not reach `main` because the site does not build with them: it does not push to `main` but to the branch `desk-build-failed/<day>-<run>`, opens a draft pull request on it, and says in it which checks of the audit failed (`--audit-log` is the report of the audit; none means that the build failed before it).

`--config <path>` is the path of a YAML file of settings (from the folder the command is run in), laid over the defaults of `desk/src/config.ts`: how recent a story must be (`recencyHours`), how many candidates reach the selecting model (`shortlistMax`) and how many of them one source can have (`shortlistPerSource`, 3 by default, so that a source that publishes a great deal cannot fill the shortlist), the fewest claims a piece needs, the rounds of revision (`maxRevisionRounds`) and how many more rounds a draft gets when only the model check rejects it in the last one (`modelCheckRevisions`, 1 by default; a blocker of the gate does not get them), how many runs one day may have (`maxAttemptsPerDay`), the user agent, the most characters of one page that are read (`maxPageChars`, 150,000 by default; a longer text is cut at the last paragraph or line break past half the limit, else at the last space, and the artifact says so), the budget, the models, the folders `runDir` and `evidenceDir`, which are below the folder the command is run in when they are relative, and `prices` (what a million tokens cost, which only `desk tune` reads). The setting `evidence` (`kind: local` or `kind: r2`) chooses the evidence store (see The evidence store); the address, the name and the keys of a bucket are not settings, and a file that carries one is refused like any other setting that does not exist. A file that cannot be read, or that has a setting that does not exist or a value that is not allowed, is a mistake in the arguments (exit code 2) and names the file and the setting. A live run (`--sources live`) with a user agent that links to an `.example` address is refused with exit code 2, because the default user agent links to agenticmediahouse.example, which does not exist: a live run needs a file of settings with the real address of the /method page. A run on the made-up world and a replay ask no site and are not refused.

`desk.config.yml` at the root of the repository is the file of settings of the daily run: the real user agent (it links to the /method page of the live site), `evidence: { kind: r2 }`, the folder of the runs, `maxAttemptsPerDay` and the budget of a run. It is committed, so it holds no secret, and it names no model (the models are the defaults of `desk/src/config.ts`). The key of the model and the four variables of the bucket come from the environment, never from this file. `desk/test/production-config.test.ts` loads it and checks all of this.

The exit code is 0 for a run that published, held or found no story (and for a day that `--skip-if-done` left alone), for a replay that came out equal and for a correction that was made, 1 for a run that failed or was refused, for a replay that differs and for a correction that was refused or failed, and 2 for a mistake in the arguments.

`npm run desk:demo` runs the whole pipeline once as one command, `desk run --dry --client fake --sources fixtures`, and then replays the run. It exits 0 only if the made-up story ended published in a dry run, nothing was written to the site and git was not asked to commit, and the replay found every artifact equal. It is a step of `npm run verify`. The last line it prints says what it has shown, and what it has not: `desk demo: ok: completed as published (dry run, scripted model and verifier): this proves the plumbing and replay equality, not model quality`. The model and the verifier of the demo are scripts written to pass, so it shows that the stages fit together and that a run can be replayed, and nothing about how well a real model writes or a real verifier judges.

## Holds and corrections

**A held piece goes to the owner as a draft pull request.** When a run that is not dry ends held, and the program can reach GitHub, the Desk does this, and stops at the first step that fails. All of it is built and tested with a stand-in for GitHub and a script in the place of `git` and `gh`; it has never been run against GitHub itself.

1. It keeps the draft in `runs/<date>/held/`, as it always did.
2. It commits the two files of the piece to a branch `hold/<day>-<slug>`: the article and the ledger, exactly as they would have been published, except that the ledger says `release: owner` (the receipts page then says that the owner released the piece) and that its gate route is `hold` with the reasons of the hold. The branch is made beside the checkout, from the commit that `main` is on, so the checkout is never changed: no switch of branch, no file written, whatever goes wrong.
3. It pushes the branch to `origin` and opens a draft pull request into `main`, titled `Held: <headline>`. The text says what was held and why (each reason in the words of the holds page of the site), what the gate and the model check said, and how to publish or discard the piece. What a model wrote (the headline, the messages of the failures, the notes of the model check) is in fenced blocks, so that it cannot become a link, a mention or a heading.
4. Only then does it record the hold in the desk state, with the address of the pull request as `prUrl`, and commit that to `main`.

**The name of the branch is a name for each try.** It is `hold/<day>-<slug>` for the first try of a day and `hold/<day>-<slug>-t<n>` for the n-th (the number is the try that the record of the run says). Before the branch is made the Desk asks the remote which of the names from its own try on it already has (`git ls-remote`), and uses the first that it does not have: a scheduled job starts from a fresh checkout, with no record of the earlier tries, and so is the first try as far as it knows, but the remote remembers the branch that an earlier try left. A slug that is too long is cut at the last hyphen that fits in 80 characters, never in the middle of a word and never leaving a hyphen at the end, and the mark of the try is counted in the 80. One pattern holds the name for every part that handles it (`desk/src/run/branches.ts`: git, which makes and removes the branch, and the forge, which pushes it and opens a pull request on it, accept exactly the same names).

You publish the piece by marking the pull request ready for review and merging it: the two files arrive on `main`, and the hold stays in the desk state. You discard it by closing the pull request. A dry run never touches GitHub.

**A hold is remembered, so that a story is not held twice.** The desk state records, with each hold, the slug of the held piece and the address of the story that the Desk chose (`slug` and `sourceUrl`; a hold recorded before they existed has neither, and covers nothing). A hold covers its story for 14 days after it was recorded, which is the window that the gate uses for the titles of published pieces (`titleWindowDays`): the index of what is published, which Discover, Select and the gate's slug check read, has its slug among the slugs and its address among the addresses. So the Desk does not choose the same story again while its pull request is open, neither on the same day nor on the next, and two runs in a row cannot open two pull requests for one story. A hold from yesterday covers its story, a hold from 15 days ago does not. A pull request that you close keeps its story out of the pipeline until the 14 days are over. To let the Desk try the story sooner, delete its hold from `site/src/data/desk-state.json` (the Desk never deletes a hold itself), commit that, and, if the day already has a run that held, run `npm run desk -- run --force-new`. Only the story that was chosen is remembered, by its address: the same story reported at another address is another candidate. The holds page of the site shows the date, the beats and the reasons of a hold, and neither the slug nor the address.

What the program needs for this: `git` and `gh` (the command line of GitHub) on the path, `gh` logged in (or `GH_TOKEN` in the environment), a remote called `origin`, and the checkout on `main` with nothing uncommitted where the Desk writes (the desk state and the folders of the pieces and the ledgers). The programs are started with a list of arguments and never through a shell, the body of the pull request is passed as a file, and the branch must have the form `hold/<day>-<slug>` before anything is run.

**When a step fails, the run fails.** It ends `failed` at the stage `hold`, the next try of the day is allowed, the held draft is still in `runs/`, the desk state has no hold, and `main` gains only the record that the run failed. A draft that cannot be written as a piece (a sentence cites a claim that does not exist) is the one case that is not a failure: it has nothing to merge, so no pull request is opened, the hold is recorded without an address, and the reason of the run says so.

| Step that fails | What is left |
|---|---|
| Uncommitted changes where the Desk writes, no remote, the checkout is not on `main`, the branch or the slug is taken | Nothing was made |
| The push | The branch is removed |
| The pull request, after the push | The local branch is removed. The branch is on the remote, and the error says so: open the pull request from it by hand, or delete the branch |
| The record of the hold, after the pull request | The pull request and the branch stay, and the error says where the pull request is |

**A piece that is published and wrong is corrected in public, and never deleted.** `npm run desk -- retract <slug> --reason <text>` adds a record `{ at, slug, kind, note }` to the corrections of the desk state, sets `updatedAt` in the frontmatter of the piece to the UTC day of the record (the site refuses to build a piece whose `updatedAt` is not the day of its latest correction, and one that has a record and no `updatedAt`), and commits the two files in one commit. `--kind retraction` records a retraction; `--dry` says what would be done and writes nothing. The reason is one line of at most 500 characters (white space is made one space, control characters are refused), and it goes into the desk state as the note and nowhere else: not into the piece, not into the ledger, not into the message of the commit. The rest of the piece is the same, byte for byte, and its ledger is not touched. A second record on the same day changes only the desk state. The command refuses a slug that is not on the site (a piece that was held is on its pull request until you merge it), a piece or a desk state with uncommitted changes, and a clock that is before the day the piece was published or before an earlier record of the same piece. It does not push or deploy: the notice reaches readers when the commit reaches `main` and the site is built.

## The evidence store

**What is kept.** Every page that a run reads is kept as a **snapshot**: the text of the page, named by its SHA-256, with where it came from (the address that was asked for, the address after the redirects, whether the source is tier 1 or tier 2, and when it was fetched). A claim of a piece points at a snapshot by its hash, so anyone who has the text can check that it is the text that the claim was taken from. A snapshot is never changed: putting a text that is kept already changes nothing, and a snapshot whose text no longer matches its hash is refused when it is read back, which is worse than one that is missing.

**Where.** The setting `evidence.kind` of a file of settings (`--config`) chooses the store. `local`, the default, is a folder (`evidenceDir`, `evidence/`, which git ignores): two files for each snapshot, `<hash>.txt` and `<hash>.json`, and the snapshots that were kept in a folder `published` below it. The folder is gone when a machine that starts from a fresh checkout every day ends its job, so a workflow uses the other kind. `r2` is a **private bucket on Cloudflare R2**, reached through its S3-compatible interface: `desk/src/run/r2-evidence.ts` makes the requests (a `PUT`, a `GET` or a `HEAD` of one object, at the address `<endpoint>/<bucket>/<key>`), and `desk/src/run/sigv4.ts` signs every one of them, with AWS Signature Version 4 written with `node:crypto`, each step of which is tested against the worked examples that Amazon publishes. No package was added.

**Which variables.** A bucket is described by four variables of the environment and by nothing else: `R2_ENDPOINT` (`https://<account>.r2.cloudflarestorage.com`, with no path), `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`. They are never read from a file of settings, because a file of settings is committed (a file that carries one is refused as a setting that does not exist), and there is no flag to choose the store: the settings decide. A run that asks for `r2` and does not have all four is refused with exit code 2, naming the ones that are missing and never what any of them holds, and a value that the store refuses (an address that is not https, a name that is not a bucket name, a key that cannot sign) is refused the same way. No message, log, record or artifact of the Desk has a key in it: the secret is used to sign and nowhere else, and every message of the store has both keys taken out of it. `--sources fixtures`, the made-up world, is refused with `r2`: nothing made up may be put in the bucket.

**What is written.** Two kinds of object, and nothing else:

| Key | What it is | Written when | Removed |
|---|---|---|---|
| `pending/<hash>` | The text of a page that a run fetched, with where it came from as the metadata of the object | Fetch, for every page, in every run, dry or not | By the bucket, 90 days after it was written (a rule on the prefix, set when the bucket is made) |
| `published/<hash>` | The same, for a snapshot that a published piece cites | Publish, before the piece is written, for each source of its ledger | Never |

`<hash>` is 64 lowercase hex characters. A piece that is held, a day with no story and a run that fails leave their snapshots in `pending/` only, and a dry run puts and reads but never keeps. Reading and asking look in `pending/` and then in `published/`, so a snapshot that was kept can still be read after its first copy has expired.

**What a run does with it.** Fetch puts each page. Before Extract takes a word from a page, the run reads every snapshot back (the stage `evidence`): the text must be the one that was fetched, and a store that has lost or changed it ends the run. Publish keeps the snapshots that the piece cites before it writes the piece. A store that cannot be reached, that refuses, or that holds what has been changed, at any of the three, ends the run `failed` at the stage `fetch`, `evidence` or `publish`, with nothing published; the next try of the day (up to `maxAttemptsPerDay`) is the retry. The error says what kind of trouble it is: `unreachable` (no answer, a 408, a 429, a 5xx, a redirect), `denied` (a 401, a 403, any other refusal), `tampered` (the text does not match its hash, or its record is not valid) or `missing`.

**What a message of the store says, and does not.** An error of the store says what was asked (`GET pending/<hash>`), the status that came back and the start of what the bucket or the network said, cut at 200 characters. It never has the address of the endpoint, which has the id of the Cloudflare account in it, the name of the bucket, or either key: they are replaced by `<r2-endpoint>`, `<bucket>` and `<key>`, whatever the network or the bucket echoed (a failure to look the address up, a certificate that does not match it, the body of an error that repeats the request, a form of any of them that is escaped as a path or a header is). A message goes into the record of the run, into its log, and, for a run that fails, into the log of a workflow of a public repository, where GitHub hides only a whole secret and not an address that has an account id in it. The name of the bucket is taken out of what the network or the bucket said and not out of the sentences of the store itself.

**Who can read it.** The bucket is private: no public access, no `r2.dev` address and no custom domain are set on it, and the Desk never sends an access-control header, so every object has what the bucket gives by default. A snapshot can be read by the holder of a key that the bucket takes, which is the token that the Desk signs with (limited to this bucket) and the owner of the Cloudflare account, and by no one else. The text of a page never leaves the bucket: the repository has the hash of each snapshot and a short quotation of each claim (at most 300 characters), and what a workflow uploads as an artifact must not have page text, because the artifacts of a public repository are public.

**How the bucket is made.** The runbook makes it, once, outside this plan: a bucket that is private; a rule that deletes the objects of the prefix `pending/` 90 days after they were written (and none for `published/`); an API token that may read and write objects, limited to this bucket; and the four variables set as secrets of the workflow. The store is built and tested with no bucket and no network: every test gives it a bucket made of memory that answers as S3 does and refuses a request whose signature it cannot check. It has never been used against Cloudflare, so what R2 answers to a real request is for the first real run to confirm.

## The daily workflow

`.github/workflows/desk.yml` runs the Desk. It starts at 04:30, 06:30 and 08:30 UTC every day and by hand (Actions, Desk, Run workflow), one run at a time (the concurrency group `desk`, which never cancels a run that has started), and runs `npm run desk -- run --config desk.config.yml --skip-if-done` after a checkout with the whole history, Node from `.nvmrc` and `npm ci`. The first start of a day does the day's work; the second and the third do nothing when the day already has a run that did not fail, and run the day again when it did. The commits of the Desk are by `github-actions[bot]`.

- **Secrets.** `ANTHROPIC_API_KEY`, `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` are secrets of the repository, and they are given to the one step that runs the Desk, in its `env`, and nowhere else: no command in the file has an expression, names a secret or prints the environment. A test fails if that stops being true.
- **The site is built first.** What a run committed reaches `main` only after the site has been built with it (`npm run build`, with the same `SITE_URL` as the deploy) and the audit of the production build has passed (`npm run audit:prod`). The gate knows nothing of Astro or of the audit, so a piece that clears the gate can still break the build, and a broken build on `main` would stop every later deploy, a retraction included. When either fails, the push to `main` does not happen: the step `desk push --branch-only` puts the commits on the branch `desk-build-failed/<day>-<run>` and opens a draft pull request on it, whose text is fixed sentences, the ids of the checks that failed and their numbers of problems, and nothing that the report says about a page, and the job fails. The build and the audit run whenever the Desk ran, a day that is done included, because then they check `main` itself. A test (`desk/test/workflows/build-before-push.test.ts`) runs the steps of the workflow in order, with the conditions that each has, over a made-up GitHub, and shows that a failing audit or build ends with `main` as it was.
- **What is pushed.** A run that is not dry makes one commit, whatever way it ends, and a held piece's branch is pushed by the Desk itself. The step after the run is `npm run desk -- push`, which fetches `origin/main`, counts what `main` has that `origin/main` has not with `git rev-list --count origin/main..HEAD` (never from an upstream, which a checkout may not have) and pushes it with `git push origin HEAD:main`. It never fails open: any error of git, a checkout on no branch or on another branch than `main`, a missing remote and a remote with no `main` are exit code 1, and only a count of 0 is "nothing to push". A push that is rejected because somebody else pushed to `main` in the meantime (the owner merging a held piece, say) is made again after a fetch and a rebase onto `origin/main`, up to 3 more times. When the commits cannot be put on top (the desk state, which every run changes, is the usual cause), or `main` does not take a push at all, the rebase is undone and the commits are pushed to the branch `desk-rescue/<day>-<run>`, a name that no earlier run has, `main` is left as it is, and the step fails and says where the commits are. A push by the token of a workflow starts no other workflow, so when something was pushed the last step starts the deploy workflow by hand (`gh workflow run deploy.yml --ref main`), which is why the token may start workflows.
- **A rehearsal, and the switch of the schedule.** A start by hand has one input, `dry` (Actions, Desk, Run workflow, and tick the box; or `gh workflow run desk.yml --ref main -f dry=true`). It runs `desk run --dry` and not `--skip-if-done`: the real sources, the real model and the real bucket (the pages go to `pending/`), every artifact written, and nothing published, committed or pushed. The site is still built and audited, the run is packed and the pack is kept, and the push, the branch of a build that failed and the deploy are skipped: they are conditions of the steps, and not something that the Desk happens not to do. The schedule is a different matter. The job runs when the schedule starts it only if the variable `DESK_SCHEDULE` of the repository is `on` (`gh variable set DESK_SCHEDULE --body on`), and a start by hand always runs. So the workflow can be on the repository, and be rehearsed, long before the Desk is let go, and the first push of the repository cannot start a Desk that publishes; setting the variable to anything but `on` stops the daily run. `desk/test/workflows/dry-run.test.ts` runs the steps of the workflow for each case.
- **What each step can reach.** The checkout is made with `persist-credentials: false`, so it leaves no token in `.git/config`, and `npm ci`, which runs the install scripts of every package in the tree, runs with no token in reach. The token of the workflow (`GH_TOKEN`, in the `env` of the step) is given to the four steps that need it: the run of the Desk, which pushes the branch of a held piece and opens its pull request; the push; the branch of a build that failed; and the deploy, which only asks `gh` to start a workflow. Git is given the token for github.com alone, by the environment, in one place (`.github/scripts/github-auth.sh`: a basic credential built inside the step, never in an address, on a command line or in a file, and printed nowhere). The programs that the Desk starts, `git` and `gh`, are given an allow-list of the environment (`PATH`, `HOME`, `LANG`, `TMPDIR`, the variables of git, and the token of GitHub for `gh` alone) and not the whole of it, so that the key of the model and the variables of the bucket are in the environment of the Desk and of no child of it. Tests parse the three workflows for each of these rules and start real children that print what they were given.
- **What is kept.** A pack of the run is kept as an artifact for 14 days, even when the run failed, and the folder of the runs is not. Artifacts of a public repository can be read by anyone, and what a run writes in its folder is what models and pages wrote: the quotations of the claims (up to 300 characters each, and there are many), every sentence of every draft, the reasons of the model check (as long as a model likes), the recorded replies. So `npm run desk -- pack-artifact` makes, of the folder of the day, `run.json` and one small file for each stage, and each is made by naming the fields that go in, one by one: the outcome, the names of the stages, the try, counts, the codes of the checks (a closed list, which the site has a label for), the counts of the verdicts of the model check, hashes, sizes and durations. No reply of a model, reason of the verifier, sentence of a draft, quotation, title, address or word of a page is ever in it. A field that a stage adds later is not in the pack until somebody adds it to the list, a code that is not on the list is counted and not copied, and a pack of more than 24 KB (or a file of it of more than 8 KB) is an error and not a pack. The upload takes that folder and nothing else; a day that was done has no folder, and nothing is uploaded. `desk/test/run/pack.test.ts` packs a run whose every free text is a hostile string of 10,000 characters and finds none of it, and `desk/test/workflows/uploaded-runs.test.ts` lists every kind of file that a run writes (a new kind fails until somebody decides whether it may be packed).
- **Failure.** The job fails when the run fails (exit code 1), so GitHub tells the owner.
- **What is not proved.** A workflow cannot be run anywhere but on GitHub. The tests read the file with a YAML parser and run its two small scripts in a made-up repository; the first real run (docs/runbook.md) is the proof, and the versions of the actions (`actions/checkout`, `actions/setup-node`, `actions/upload-artifact`) were not checked against GitHub, because nothing in the plan may use the network: the runbook says how to check them. The workflow assumes a repository where the token of a workflow may push to `main` (no branch protection that forbids it) and may open pull requests (a setting of the repository), which only the first real run can show.

## The deploy workflow

`.github/workflows/deploy.yml` builds the site for production and puts it on Cloudflare as a Worker that serves static assets, not as a Pages project (Cloudflare's command line recommends Workers for every new project). It starts on every push to `main` and by hand: the daily workflow starts it by hand after it pushes, because a push by the token of a workflow starts no other workflow. Its steps are `npm ci`, `npm run build`, `npm run audit:prod` and `npx wrangler deploy`, and a step that fails stops the ones after it, so a site that does not build or whose audit fails is never deployed. A newer deploy cancels an older one that is still running (the concurrency group `deploy`).

- **The address.** The build is given `SITE_URL` from the repository variable of that name, or `https://agentic-media-house.joshi-alok.workers.dev`, where the site already is, when there is none. When the site gets a domain of its own, the variable and the user agent of `desk.config.yml` change together, and a test fails if the two hosts differ before then.
- **The settings of Cloudflare.** `wrangler.jsonc` at the root holds the settings that are not secret: the name of the Worker (`agentic-media-house`), the date of the runtime, the address at `workers.dev`, and `assets.directory`, which is `./site/dist`, the folder that the production build writes and the audit reads. Without a settings file `wrangler deploy` refuses to run at the root of an npm workspace; with this one it runs there (`npx wrangler deploy --dry-run` shows that without deploying). A test holds the file to the schema that the installed wrangler ships.
- **The program.** `wrangler` is a development dependency of the root package, at one exact version, so that what is deployed with is what was tested with.
- **The secrets.** `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are secrets of the repository, given to the one step that deploys, in its `env`, and nowhere else. The account id is in no committed file.
- **What is not proved.** A workflow cannot be run anywhere but on GitHub, and no deploy has been made by this workflow: the one deploy that exists was made by hand. `desk/test/workflows/` reads the three workflows and `package.json` and fails when they disagree (every `npm run` has its script, one major version for each action, Node from `.nvmrc`, secrets only in an `env`).

## The tuning harness

`npm run desk -- tune --urls <file>` tries the pipeline on real pages and says what each step found, so that what the models are told can be tuned from evidence. `<file>` lists addresses, one to a line (`#` starts a comment); it needs `--config desk.config.yml` for the real user agent, as a live run does (a user agent that links to an `.example` address is refused with exit code 2). Each page is fetched as the Desk fetches (`robots.txt` honoured, at the pace of the settings), read and cut to `maxPageChars` as Fetch reads and cuts it, sorted by `sources.yml` (an address on a host that the registry does not list is not fetched at all, and a page that was redirected to another kind of source is not read), and sent through Extract, Compose and Verify with `--client api` (the default, which needs `ANTHROPIC_API_KEY`) or `--client fake` (a scripted model that proposes no claims: it tries the fetching and the sorting and costs nothing).

- **What it prints.** For each page and each trial (`--trials N`, 1 to 10, 1 by default, runs the model steps N times on a page that is fetched once): the kind of source, the claims proposed, the claims dropped (counted under each rule that dropped them), the claims that survived, what the gate said of the first draft (its failure codes), the notes and the words of the draft (the findings that did not block it, and the length of its body, so that a trial shows whether the writer padded or stopped), what the model check said of the first draft that the gate cleared (how many sentences and headings were entailed, not entailed, ambiguous or without a verdict, and how many claims had a basis or status that was not supported), how the verification ended, and the tokens. Then the total. A page that cannot be tried (robots.txt forbids it, it is not found, it is of no known kind) says why, and a trial that fails says why and the next page is tried; neither makes the exit code 1.
- **The profile.** `--profile brief|digest|explainer` judges the drafts against the ranges of a kind of piece (the length of the opening, the number of key takeaways, the length of the body and the share of analysis) instead of the defaults of the gate, and tells the writer the same ranges; `tune.json` records the profile. The words and the notes of each draft are shown with or without it.
- **Dollars.** The Desk does not know what a model costs and never guesses. The settings may have a `prices` block (`inputPerMillion` and `outputPerMillion`, in dollars, which the owner reads from the price list), and then each trial and the total show dollars. Without it the table shows tokens only, and it shows no dollars when extract, compose and verify are not one model, because the block holds one price.
- **The budget.** `--max-calls M` (1 to 200, 40 by default) is the most model calls that the whole invocation may make, counted where a call reaches the model, each retry included. When they are spent the invocation stops where it is, with the reason in the table and on the error output and exit code 1, and what was done is kept. Each trial is also held to the budget of the settings, as a run is (calls, tokens in, tokens out): a trial that spends more fails, and the next has the whole budget again.
- **What it writes.** Only below `runs/tune/<stamp>/`: `tune.json` (the table as data, checked against a schema and rewritten after every trial, so that a program that stops leaves what was done), the artifacts of each trial in `<page number>/trial-<n>/` (`04-extract.json`, `05-compose.json`, `06-verify.json`, and `log.txt`, the lines that the stages logged, which hold counts and codes and no text of a page or a model), and the text of the pages in `evidence/`. It never touches `site/`, the desk state or git, and it never uses the evidence store of the settings, so a page that is only being tried does not reach the bucket. The pages are third parties' text: the folder is not committed (git ignores `runs/`) and the daily workflow does not upload it.
- **What is not proved.** It has been run only against scripted models and made-up pages. How it behaves on real pages and a real model is what the first trials show (docs/runbook.md, steps 17 to 21).

## The runbook

`docs/runbook.md` is the list of operations that put the publication on the air, in seven parts: before anything goes outward (check the repository for keys and e-mail addresses, rewrite the author and committer of every commit to the no-reply address of GitHub), GitHub and Cloudflare before the first push (the empty public repository, the permissions that the workflows need, the private bucket with its rule that deletes `pending/` after 90 days, the access key of the bucket, the token that deploys, the secrets without the key of the model, and the proof that an anonymous request to the bucket is refused), the first push (CI, the first deploy by the workflow, the schedule that stays off until a variable of the repository says `on`, how to redo the first deploy by hand, and the check that GitHub will tell the owner when something fails or is held), the first contact with a real model (`desk tune`, the verifier evals, changing the prompts), the shadow week (a rehearsal on GitHub with `dry`, a rehearsal of a held piece in a private repository that is deleted afterwards, a dry run each day, what to record, replaying a day), going live (freezing the floor of the verifier, the four questions that the trials leave open, turning on the flags of `site/src/lib/live.ts` in a change of its own, switching on the schedule), and later (a domain of one's own, taking a piece down without losing the correction, stopping the run, putting the previous site back, rotating the keys). The US$10 of the plan is enforced by the spend limit that the owner sets on the key in the Anthropic Console: the Desk's own limits are of calls and tokens.

- **Each step has its commands and what to expect.** A step marked *outward* changes something outside the machine (GitHub, Cloudflare, the model, money) and is not run without the owner's go-ahead for that step.
- **No secret is on a command line.** Secrets are kept in files under `~/.config/agentic-media-house/` that only their owner can read, and a command reads them from the file (`gh secret set NAME < file`, `gh secret set --env-file file`, or `NAME="$(cat file)" command`).
- **What the tests check of it.** `desk/test/runbook.test.ts` fails when a step has no command or no expected result, when an outward step is not marked, when a command names an `npm` script or a `desk` option that does not exist, when it names a file or a workflow that is not in the repository, when it names a check or a code of the gate that does not exist, when the secrets that it lists are not the ones that the workflows read, when the times of the schedule differ from `desk.yml`, when the variable or the input that it gives to the workflow is not one that the workflow has, and when anything in it is shaped like a key or an e-mail address, or a secret is on a command line. It runs the two searches of its first step over the repository, runs the rewrite of the history on a made-up repository, and runs the command that makes the registry of the rehearsal of a held piece.
- **What is not proved.** Every operation of it meets GitHub, Cloudflare or a real model, so none can be run by a test. The first time that any of it is run is what shows whether it is right, and what it shows is recorded.

## The verifier evals

`npm run evals:verifier` measures a verifier. `desk/evals/verifier-set.json` holds sixty sentences, each with the passages that it is judged against: for each of twenty sets of passages, one sentence that they support, one that says something they do not say, and one that changes what they say in a small way. `desk/evals/run-verifier.ts` runs a model client over the set through the verifier's own prompt and the reading of its reply that the Verify stage uses, and prints precision and recall by label and overall. With no arguments it runs a scripted verifier that knows the answers, which proves the wiring and measures no model. `--client api --model <name>` asks a real model (it needs `ANTHROPIC_API_KEY`), `--batch <n>` sets how many sentences go in one call, and `--min-precision` and `--min-recall` (numbers from 0 to 1) make the command exit with 1 when a score is below them. No floor is set: what a verifier must score is decided when real models have been measured.

## What the Desk does not check

Models propose and code disposes, and the code has limits. These are the ones that are known, so that nobody reads the checks as more than they are.

- **Text that a style sheet hides.** `extractPage` leaves out an element that hides itself in its own markup (the `hidden` attribute, `aria-hidden="true"`, an inline style of `display:none`, `visibility:hidden` or `font-size:0`) with everything in it, and it leaves out `<template>`. It does not read the style sheets of a page. Text that a class hides, that is moved off the screen, that is the colour of its background or that has an opacity of 0 is read as text of the page, and a quotation of it passes the check that the quotation is on the page. The content of `<details>` is kept on purpose: a reader sees it by opening it.
- **The date of a story that has none.** A headline link on a newsroom page has no date, so a story that is found there can be any age. The Fetch stage asks its page for one (`publishedAt` of `extractPage`: the structured data, the `article:published_time` meta tag, or the first `<time datetime>` of the article; a page of plain text or markdown gives none) and ends the run with no story, with the reason `stale-or-undated`, when the page gives none or one outside `recencyHours` of the run. A page can say what it likes about itself, so a page that claims to be new is believed: this stops an old announcement that sits on a newsroom page, and not a page that lies.
- **Which addresses the fetcher goes to.** `HttpFetcher` looks a host up before the first request and before every hop of a redirect, and refuses (the error kind `address`) a name that has any address that is not public (loopback, private, link-local, the metadata service of a cloud, shared, documentation, multicast), a host written as a number, `localhost` and an address with a user name in it. The name is looked up by this check and again by the transport, so a name server that answers differently the second time (DNS rebinding) is not stopped; closing that needs the transport to connect to the address that was checked. `FixtureFetcher` serves files and is not checked.
- **Analysis sentences.** A piece may hold sentences of the Desk's own analysis, which the page labels Analysis. The gate reads them for where they stand (not in the title or the description), for the numbers, dates, words of amount and names they bring in that no factual sentence contains, and for how they begin (with a capital letter or a digit, and with a function word or a word of the quoted passage, the name values or the outlet of a claim they cite) (G7), and the model check (G10) then judges each of them beside the passages of the claims it cites (all the claims the piece cites, when it cites none), and rejects one that adds an entity, an event, a figure or a claim of fact that they do not support. The share of the body that analysis takes (a fifth by default) is only noted on the receipts page, and the gate does not stop a piece for it. A model can miss what is wrong with an analysis sentence, so a wrong analysis can still be published. The page labels every analysis sentence, and the receipts page notes a piece whose analysis goes over the target share; that shows the exposure and does not remove it.
- **Values that are not compared.** Extract holds the `normalised` form and the `unit` of every value of a claim to its `raw` text, and drops the claim (the reason `value-normalised-mismatch`) when they say something else: a number is read as the gate reads it (digits or number words, with the unit table of the gate), a date as ISO at the precision it is written, a name as lowercase with single spaces. A value whose `raw` text is not a number token, number words or a date that the gate reads (a vague amount such as "half", a lone "one", a date in another shape) is not compared with its normalised form, because the gate does not read it as a figure either. The check is made on claims, which are all that Extract makes; the gate itself still takes the `normalised` form on trust for a number in words.
- **The headline in a pull request.** The title of a hold's pull request is `Held: ` and the headline that the model wrote, on one line and cut at 100 characters. It is passed to `gh` as one argument and is never run, but it is shown on GitHub as it is written, and GitHub may turn a `#12` in it into a link to that issue or pull request. The text of the pull request has everything a model wrote in fenced blocks; the title is the one place where it is not.
- **Commits that did not reach `main` because the site does not build.** They are on a branch and in a draft pull request, and nowhere else: the desk state of `main` knows nothing of the run, so the next start of the day runs the day again, and while the build stays broken that can be a pull request at every start, three a day. The runbook says to look at the first one.
- **A branch with no pull request.** A branch that was pushed when the pull request could not be opened stays on the remote (the Desk removes only its own copy). The error says its name and how to delete it (`git push origin --delete <branch>`); or open the pull request from it by hand. The next try of the day does not push to it: it uses another name (see the name of the branch, above), so it is never refused as a push that is not a fast-forward. The branches that the tries leave are not cleaned up: they stay until somebody deletes them.
- **Evidence of a piece that the owner releases.** Only a run that publishes keeps snapshots. A piece that the owner publishes by merging the pull request of a hold is published by GitHub, so nothing keeps its snapshots: they are in `pending/`, and the bucket removes them 90 days after they were written. Merge a hold within 90 days, or keep the snapshots by hand; a command that keeps the snapshots that a piece on the site cites is not built.
- **The store does not retry.** A request to the bucket that fails once fails the run. A day that failed is tried again by the schedule (up to `maxAttemptsPerDay` runs a day), but a bucket that is down for hours fails every try.
- **Copies of snapshots of a piece that was not published.** Publish keeps the snapshots before it writes the piece. If the commit then fails, the copies in `published/` stay, though the piece was not published: each is a copy of a text that is in `pending/` anyway.
- **A record that is too long.** The record of a snapshot is the metadata of its object, and S3 takes 2 KB of metadata. A page whose address is so long that its record does not fit (roughly 1,500 characters of address, fewer when the address after the redirects is another one) fails the run at Fetch.
- **Claim ids in a prompt.** The ids that a composer writes for the claims a sentence cites are strings, and the schema of its reply lets any string through. Before they are put in a prompt outside a block (the line in front of an item that is sent back for revision) they are filtered to the ids of claims that exist, which look like `c-1`; the rest are left out and logged.

## Fixtures

Until the Desk has published something there is nothing real to show, so the site is built and tested on made-up pieces. All of it is fictional: the company is Fixture Robotics, the product is the FX-1, and every address is on `*.example`. The outlet that one piece cites, Mercer Wire, is made up too.

- `npm run fixtures:generate --workspace @robywire/site` writes the fixture pieces, their ledgers and a desk state into `site/src/content-fixtures/`. It starts from the golden piece in `gate/src/fixtures/`, makes variants of it, and runs each through the real gate and the real renderer, so the fixtures are what the Desk will produce.
- Five pieces are made. Four are ordinary: the gate clears them and their ledgers say `release: auto`. The fifth (FX-5) rests on one sentence that Mercer Wire reported; it stands for a draft that the model check could not clear (`G10_AMBIGUOUS`: it could not tell if a sentence was supported) and that the owner then released: its ledger says `release: owner`, its article carries the Unconfirmed. label, and its receipts page says who released it.
- The generated files are committed. `npm run fixtures:check` fails if they are out of date.
- The site reads `site/src/content-fixtures/` only when `ROBYWIRE_FIXTURES=1`, which `npm run build:fixtures` sets. Otherwise it reads `site/src/content/`, which holds no pieces. A fixture build shows a ribbon at the top of every page that reads FIXTURE DATA and says it is not real reporting. A production build has neither the ribbon nor the words Fixture Robotics anywhere, and `npm run audit:prod` fails if it does.

## What the site refuses to build

A piece is two files: the MDX that readers see and the ledger JSON behind its receipts. `site/src/lib/match-pieces.ts` joins them and stops the build, with a message that names the piece, when they do not belong together:

- the ledger has no piece, or the piece has no ledger, or their slug, date or categories differ;
- the `title` or the `description` of the MDX is not what `renderHead` (in `gate/src/render/head.ts`) gives from the title sentence and the description sentence of the ledger, or the `title` of the ledger is not its own title sentence;
- the body of the MDX is not exactly what `renderBody` (in `gate/src/render/body.ts`) writes from the ledger, so a hand edit of the article, or of the ledger, is caught on the first build;
- a correction or retraction is recorded in the desk state for the piece and its `updatedAt` is not the day of the latest one, or it has an `updatedAt` and nothing is recorded.

## The audit

`npm run audit` reads the built pages in `site/dist` and checks them against the rules of the design and of the content. The checks are listed, with a sentence for each, in `site/scripts/audit/checks.mjs`; every check has a test that gives it a page it must accept and a page it must reject. They include: every page parses and has one `h1`, a title, a description and a skip link; no images, no italics, no web fonts, no border over one pixel, no rounded corner; every colour, in the CSS and in the colour attributes of an inline SVG, is one of the design tokens in `site/src/styles/tokens.css`; every internal link and `#fragment` resolves; every article links to its receipts page and has `NewsArticle` data; every claim marker in an article leads to its claim; every article shows its fact card, a figure with a label that holds an inline SVG drawn in the tokens' colours; and the feed, the sitemap, `robots.txt` and the 404 page are there and agree.

## Reading the scoreboard

`npm run evals:seeded` is the proof that the gate works. It takes one golden piece, breaks it in a known way at least once for every failure code of the nine checks, and fails if the gate misses any. It writes the result to `evals/scoreboard/seeded.json`, which is committed; a test fails if the committed file is out of date, so run the command and commit the file after any change to the gate.

The site shows the same file on its `/method/` page, under the headline `N of N seeded defects caught`. Each row is one defect:

- `id` names the defect, for example `swapped-number` (a sentence says 83 kg where the cited claim says 38 kg).
- `check` and `code` are the rule and the failure code that should catch it, for example G4 and `G4_NUMBER_UNSUPPORTED`.
- `caught` is `true` when the gate reported that code, and `false` when it did not. A `false` fails the tests, and the page would show it in red as `missed`.
- `baselinePasses` says that the unbroken golden piece publishes, so a catch means the gate saw the defect and did not simply reject everything.

The scoreboard is a floor, not a proof. It says the gate catches the defects that were thought of; it says nothing about the ones nobody seeded. The independent model check and its measured accuracy come later and are not part of the scoreboard.

## CI

`.github/workflows/ci.yml` runs the steps of `npm run verify` one by one on every push to `main` and on every pull request, and `site/test/verify.test.ts` fails if the two lists differ. Chrome is already installed on the `ubuntu-latest` runner.
